需求与问题：[Issue #4](https://github.com/jiacheng299/vision-appliance-software/issues/4)、[Issue #5](https://github.com/jiacheng299/vision-appliance-software/issues/5)。基线：`463fb9b`。审查人：用户指定的 `Joe-Sun-7`。

## 使用方式和统一用语

“新建草稿”在桌面端打开右侧半屏抽屉，小屏使用全宽。填写名称、用途和首个通道的视频源后，点击“创建并配置”进入配置页；底部按钮固定，长内容可滚动。关闭有输入的抽屉会先确认，创建中禁止关闭和重复提交，超时重试沿用同一请求编号。

| 名称 | 含义 |
| --- | --- |
| 智能体 | 一种监测业务，例如仓库火灾探测 |
| 通道 | 智能体下的一组视频源，共用监测规则并统一启停 |
| 视频源 | 一个摄像头直播或录像文件，各自设置区域和录像范围 |
| 运行记录 | 某个视频源使用某份配置执行监测的记录；后台字段仍为 Run |
| 计划使用的配置 | 已发布、计划应用的版本；实际生效版本以各视频的运行记录为准 |

界面不再交替使用“通道”和“监测组”。代码中的历史函数名及接口字段不改名，用户已经保存的通道名称和历史配置也不重写。

## 已复现的代码问题

1. 公共播放器把多个字段放在同一个返回数组的监听函数中。同一视频源对象更新时，即使源编号没变，新数组也触发重建。回归测试中，5 次元数据更新产生了 5 次额外的播放会话，造成画面反复加载。
2. 智能体监控墙存在同类监听，刷新同一配置对象会清空已打开的画面。配置验证面板也会重复清空并请求同一验证结果。
3. 每条实时通知都会请求整份看板。回归测试中，100 条通知触发 100 次刷新；请求未完成时仍可继续堆积。

修复后按源编号、配置编号等实际字段分别监听；100 条连续通知合并为一次刷新，看板同一时间只保留一份刷新请求。筛选页面原有的“最新请求优先”行为不变，切换页面会取消待执行刷新。
